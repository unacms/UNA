# NEO: guide for coding agents and contributors

NEO is the web and native client for [UNA CMS](https://unacms.com). Shared code in `packages/app` runs as a Next.js site (`apps/next`) and as an Expo app for iOS and Android (`apps/expo`). This file covers how to change NEO; [README.md](README.md) covers setup, environment variables and deployment.

Paths are relative to the NEO root: `neo/` in the UNA repo, or the repository root in a fork.

## Upstream or fork: check before you change anything

| | Upstream NEO | Client fork |
|---|---|---|
| Repository | `neo/` in [unacms/UNA](https://github.com/unacms/UNA) | a fork of [unacms/neo](https://github.com/unacms/neo) |
| How to tell | the folder above `neo/` holds UNA's `api.php`, `inc/` and `modules/` | `apps/` and `packages/` are at the repository root |
| What you change | anything under `neo/` | only `packages/app/customization/` (see [Forks](#forks-and-the-customization-layer)) |
| Where it lands | a PR to unacms/UNA from a branch off `master` | the fork's own branches |

If a fork needs a change outside `customization/`, make it upstream as a PR to unacms/UNA, then sync it into the fork. Patching shared code in a fork makes every later sync conflict, and other clients never get the fix.

## Upstream workflow

- NEO is a git subtree of the UNA repo since October 2026. The rest of that repo is the UNA backend (PHP), so one PR can change an API and the NEO code that calls it. UNA's own agent notes are in the root `AGENTS.md`; the [`una-api` skill](.agents/skills/una-api/SKILL.md) covers what NEO needs from UNA services.
- Branch from UNA `master` and open the PR against unacms/UNA. Start the title of a NEO-only PR with `Neo:`, for example "Neo: allow only http(s) URLs in inline post embeds" ([#5787](https://github.com/unacms/UNA/pull/5787)).
- unacms/neo is a mirror: on every push to UNA `master`, [`.github/workflows/sync-neo.yml`](https://github.com/unacms/UNA/blob/master/.github/workflows/sync-neo.yml) runs `git subtree push --prefix neo` to unacms/neo `main`. Never commit, merge or open PRs there; one commit on the mirror makes the next push non-fast-forward and stops the sync. There is nothing to `git subtree pull` from it either: it only holds what UNA already has, and pulling an outdated copy reverts newer UNA changes.
- Run `yarn typecheck` and `yarn lint` from `neo/` before you push. The Next build ignores type errors. Neither command is clean on `master` yet, so the rule is: add no new errors. On a PR that touches `neo/`, the CI job `NEO lint and typecheck` enforces it: it runs both commands on the PR and on its base and fails when a file gains errors for a rule (`scripts/check-new-errors.js`; run it yourself the same way).

Upstream changes to `packages/app/customization/` reach every fork, so treat that folder as an interface:

- Keep each customization file a short re-export of a core default. New behaviour and new defaults go into core (`default/`, `settings/`, components), where forks can override them.
- Don't rename, move or delete a customization file, a default it re-exports (`settingsDefault`, `resourcesDefault`, `componentsMapDefault`, `skeletonsMapDefault`, `staticDefault`, `animatedIcons`, ...) or a function in `default/functions.js` without a fallback. Forks override them by name, and a rename silently orphans the override: renaming `config/images_allowlist.js` to `images-allowlist.js` did that to one fork in August 2026.
- Never add a file that forks create for themselves: `customization/config/app.config.js`, `apps/expo/eas.json`, `apps/next/public/.well-known/*`. Each one would conflict in every fork that has its own.

## Forks and the customization layer

Core code imports fixed paths under `app/customization/...`. Upstream, each of those files re-exports a default from core. A fork changes behaviour by changing what the file exports; nothing in the build swaps files.

Rules for forks:

1. Edit only `packages/app/customization/**`. Files that upstream doesn't have are yours too: `apps/expo/eas.json`, `.github/workflows/*`, `apps/next/public/.well-known/*`. Leave `.gitignore`, `.easignore`, `apps/expo/app.config.js`, `apps/*/package.json` and all core code alone; put local ignores in `.git/info/exclude`.
2. Extend defaults instead of copying them: mutate or spread the default export, so later upstream additions still reach you.
3. Keep secrets out of git. Use `.env.local` locally and Vercel or EAS environment variables for builds. Never put `UNA_API_KEY` in `config/app.config.js` `extra`: everything in `extra` ships inside the app binary, and the native app doesn't use the key.
4. Take upstream changes by syncing from unacms/neo `main` (GitHub "Sync fork", or `gh repo sync <owner>/<fork> --branch main`). After a sync, check whether a seam you override was renamed or removed: `git diff --name-status --diff-filter=DR <old> <new> -- packages/app/customization packages/app/default`.
5. Write fork-specific notes for agents in `packages/app/customization/resources/agents.md`, below its "Per-project additions" line. Agents working in a fork must read that file too.

| Seam | How to override |
|---|---|
| `settings.js` | Mutate nested keys of `settingsDefault` (`app/default/settings`, built from `app/settings/*.js`) in place, at module top level. Don't replace whole sections: some core code imports `settings/*` modules directly. |
| `translation.js` | Add or change keys in `resourcesDefault[lang].translation`. |
| `icons-svg.js` | Custom icons for web and native (inline SVG by name). They win over Lucide and over animated icons. |
| `icons.js` | Native-only icon components. Web draws Lucide icons by name from `/lucide/<stroke>/<Name>.svg`. |
| `animated-icons.js` | Spread the default registry and add keys; see [animated-icons.md](animated-icons.md). |
| `static.js` | Static components. A `components_<uri>` key also replaces that page. |
| `functions.js` | Re-exports `app/default/functions`. Declare a local export with the same name to replace one function. |
| `loading.js`, `sounds.js`, `covers/`, `splash-mockups/`, `nav/footer.web.js` | Replace the export. |
| `push.js` | Add your push provider to `pushProvidersDefault` (`app/lib/push/providers`) and name it in `notifications.push_provider`; see [Push notifications](#push-notifications). |
| `<type>/_map.js` for elements, form-fields, forms, molecules, page-layout, menu-items, units, units/content-list, units/profile-list, skeletons, workers | Import `componentsMapDefault` from the core `_map.js`, add or replace keys, re-export it. Put new components under `customization/<type>/`. |
| `design/styles/global.css`, `global.web.css` | CSS variable and `@theme` overrides (both platforms; the second is web only). Neutral fills follow your `--neutral-*` scale through `--ink`; set `--ink` in your `@variant light` / `@variant dark` blocks to tint them differently, or redefine `--color-bubble` / `--color-button` / `--color-button-hover` / `--color-code` in an `@theme inline` block (as `color-mix()`, see Styling) to change the steps. `--button` / `--button-hover` keep their old opaque values; only `bg-button-solid` still reads `--button`. On web, `.light` / `.dark` colour-scheme scopes (the header on a band, `layout.header.band_scheme`) re-declare core's semantic tokens, so set a semantic token you override on `:root` (`--accent-foreground`, ...) on `.light` / `.dark` in `global.web.css` too. |
| `design/fonts/fonts-web.js`, `design/fonts/fonts.js` | Web `next/font` variables and the native `useFonts` map. |
| `config/fonts.js` | Font family per role and platform; see [Fonts](#fonts). |
| `config/next.config.js` | Deep-merged into `apps/next/next.config.js`. Arrays are concatenated. Functions (`webpack`, `rewrites`, `headers`) replace upstream's, so define one only if you reimplement upstream's. This is the fork hook despite the "don't edit" comment at its top. |
| `config/app.config.js` | Create it. It's deep-merged into the Expo config, but `ios.infoPlist`, `ios.associatedDomains`, `android.permissions`, `android.intentFilters` and `plugins` replace upstream's when you set them. If you set `plugins`, copy upstream's full list and re-check it after every sync. A syntax error in this file is swallowed and the app builds as stock NEO. |
| `config/images-allowlist.js` | Extra image hosts, used by `next/image` and at runtime. |
| `config/package.next.js`, `config/package.expo.js` | Extra npm dependencies. The root `preinstall` script merges them into `apps/next/package.json` and `apps/expo/package.json`; don't commit those rewritten files, and restore them before a sync. |
| `resources/web/` | Flat files copied into `apps/next/public/static/` (gitignored) whenever the Next config loads: `favicon.svg`, `manifest.json` and every icon the manifest names. |
| `resources/native/` | App icon, splash and other native assets. Reference them from `config/app.config.js` as `../../packages/app/customization/resources/native/...`. Setting `icon` there is enough: UNA's iOS icon (`ios.icon`, an Icon Composer `.icon` file with its dark, clear and tinted versions) and Android adaptive icon are then left out, so the fork's icon is used everywhere. Set `ios.icon` (your own `.icon` file, or a PNG) and `android.adaptiveIcon` too for your own versions. Without any of them the app uses UNA's icon. |
| `resources/sounds/` | Your own native interface sounds (empty upstream). Core's WAV files are in `packages/app/resources/sounds/`, rendered from Cuelume by `scripts/render-sounds.mjs`; point keys of `sounds.js` at your files instead of replacing core's. See [Interface sounds](#interface-sounds). |

## Layout and stack

```
apps/next        Next.js app: route shells, proxy.js, next.config.js
apps/expo        Expo app: expo-router routes, app.config.js, config plugins in plugins/
packages/app     shared code, imported as app/...
  design/        View, Text, controls (NeoButton), theme CSS, fonts
  ui/            atoms, molecules, primitives (headless), workers
  components/    block renderers (elements), units, forms, form-fields, menu-items, page-layout, nav
  context/, lib/ state, fetcher, hooks and helpers
  default/, settings/   defaults that customization/ re-exports
  customization/ fork overrides
scripts/         typecheck.js, merge-package-customization.js, check-translations.js, render-sounds.mjs
patches/         patch-package patches, applied on postinstall
```

- Next.js 16 with React 19.2, built with webpack (`next dev --webpack`), not Turbopack. `@expo/next-adapter` aliases `react-native` to `react-native-web`. `typescript.ignoreBuildErrors` is on and `reactStrictMode` is off. `apps/next/proxy.js` is Next 16's middleware. Next ships its docs in `node_modules/next/dist/docs/`; `apps/next/AGENTS.md` (written by `next dev`) points there.
- Expo SDK 58 with React Native 0.88 (New Architecture only), expo-router and Hermes. `apps/expo/ios` and `android` are generated by prebuild and gitignored. A change to `app.config.js`, a config plugin or a native dependency needs a prebuild and a native rebuild.
- Styling: Tailwind CSS 4 on web and Uniwind (Tailwind 4 for React Native) on native. Tailwind is pinned in the root `resolutions` because 4.3.3 broke Uniwind breakpoints ([uni-stack/uniwind#668](https://github.com/uni-stack/uniwind/issues/668)).
- TypeScript 6, Node 24, Yarn 1 workspaces. No local script runs Turborepo, but Vercel builds through it, and its strict env mode hides any variable that `turbo.json` `globalEnv` doesn't list. Add a new environment variable the web build reads to that list.
- `yarn.lock` is gitignored, so every fresh `yarn install` re-resolves the ranges in `package.json`, native modules included. Don't change a dependency range in passing. To check what is installed, run `node -p "require('next/package.json').version"` from `neo/`; declared ranges differ from installed versions.
- Run everything through the root yarn scripts (`yarn web2`, `yarn native`, `yarn ios`, `yarn android`, `yarn build`, `yarn typecheck`, `yarn lint`; see [README.md](README.md)). They load `.env.local` through dotenv. Running `next` or `expo` directly skips it, and Expo bakes the variables into `expo.extra` at native build time.

## How a page renders

- UNA decides the routes. Each app has one catch-all route (`apps/next/app/[...path]/page.tsx`, `apps/expo/app/[...path].tsx`, plus the tabs in `apps/expo/app/(tabs)/tab0` to `tab4`). It asks UNA for the page with `system/get_page_by_request/TemplServicePages` and renders the returned blocks.
- Blocks render through the component registry: `components[type][name]` from `app/components/registry`. It is a plain object on purpose; a `getComponent()` call trips `react-hooks/static-components`. `components/registry-init.js` registers each type from its customization `_map.js`. Default maps load components with `next/dynamic`; on native, `apps/expo/babel-inline-dynamic-imports.js` and the Metro shim turn those into `require` calls.
- On web, `[...path]/page.tsx` is a Server Component. It fetches the page JSON with `fetch` (`cache: 'no-store'`), sending `Authorization: Bearer <UNA_API_KEY or tenant key>` and the viewer's cookies. React `cache()` shares that request between `generateMetadata` and `Page`, and `apps/next/lib/una-page-cache.js` keeps guests' results per URL and tenant for `appSetting('cache', 'una_page_ttl')` seconds (20; 30 for profiles). Only a request without cookies that can change the page, and only a reply without `user`, is cached: UNA keeps the session cookie when its owner signs in. `proxy.js` resets the cache on any sign-in or sign-out request (a non-GET API call whose route has `login` or `logout`). It renders `Root` from `app/root-client` inside `Suspense`.
- `cacheComponents` is off, so `'use cache'`, `cacheLife` and PPR don't work here. Don't add them.
- All other data is fetched on the client with `fetcher`, because the same code runs in Expo, which has no server.
- The client boundary is `app/root-client.js`, `app/root.js` and `apps/next/app/providers.js`. Most of `packages/app` has no `'use client'` and needs none. Don't remove the directives that exist, and don't turn shared code into Server Components.

## Talking to UNA

- Call UNA through `fetcher` from `app/lib/fetcher`:
  - `fetcher(path)` does a GET; `fetcher([path, token, body])` POSTs `body`. The full signature is `fetcher(req, useProxy = false, { signal, timeoutMs, maxAttempts, silent, onUploadProgress, keepalive })`.
  - It appends `&lang=`, so the path must already contain `?r=`.
  - It returns UNA's envelope `{status, module, method, params, data, hash}`; read `.data`. A body that isn't JSON comes back as `{}`.
  - GETs are retried three times on network errors, never on a timeout (`config.fetch_timeout_ms`, 30 s).
  - On web it calls same-origin `/api/...`, and `proxy.js` forwards that to UNA with the API key and the viewer's cookies. Native calls `UNA_URL` directly with `Origin: APP_ORIGIN` and the session cookie.
- Routes are `/api.php?r={module}/{method}/{class}` with `params[]=...` or `params=[...]`; the class defaults to `Module`, system services use `Templ*` classes. UNA only allows services marked safe or public. Many endpoints come from UNA data (`'/api.php?r=' + data.request_url`); fixed ones live in `appSetting('urls', ...)`.
- `fetcher` sends `X-Neo-Platform` (`web`, `ios`, `android`; web only through the same-origin proxy), so UNA's analytics records site actions with the right client; when the site keeps persistent visitor ids it also sends `X-Analytics-Vid`, so those actions join the device's visit. Pageviews and screen views go to UNA's analytics module from `AnalyticsTracker` (`app/lib/analytics`, mounted in `apps/next/app/providers.js` and the Expo tabs layout); send custom events with `trackEvent(name, props)` from the same module.
- Three places bypass `fetcher` on purpose: the web page shell above, AI chat streaming (`ui/molecules/ai-agent/helper.js`) and direct uploads (`lib/util/upload.ts`).
- If the page JSON can't be parsed (a PHP fatal or an HTML error page), web shows the maintenance screen for the whole page and home falls back to a static splash. Fix the UNA service; the [`una-api` skill](.agents/skills/una-api/SKILL.md) lists the rules, the usual cause being a block that fails for guests.
- Auth: `useCurrentUser()` from `app/context/user` returns `{ currentUser, setCurrentUser }`. `currentUser` is `null` until known, `false` for a guest and an object when signed in. `Root` and the layouts hold rendering until it is known, so components rarely need to wait themselves. The guest sign-in prompt is `layout.show_login_modal`.
- The UNA session cookie identifies the viewer. `UNA_API_KEY` identifies the NEO server to UNA and stays on the server (`proxy.js` and the page shell). Never expose it to client code or put it in `expo.extra`.
- The page shell's `Set-Cookie` never reaches the browser (a Server Component can't set cookies). On web, `proxy.js` calls UNA's `system/touch_session/TemplServiceLogin` before a page at most every six hours (sooner with a short session lifetime) and passes the session cookie it gets to the browser and the page (`apps/next/lib/session-touch.ts`). Native talks to UNA directly and needs none of this.
- Real-time updates: `subscribe(channel, event, callback)` from `app/ui/atoms/socket` returns an unsubscribe function; return it from a `useEffect`. The server is Soketi (Pusher protocol), configured in `config.sockets` (`SOCKETS_HOST`, `SOCKETS_PORT`, `SOCKETS_KEY`; off when unset). Anyone can subscribe to a channel, so an event should carry ids only; reload anything private through the API. Channels include `bx_timeline_0` (`added`, `deleted`, `edited`), `cmts_<module>_<id>` (`comment_added`, `comment_edited`, `comment_deleted`), `profile_<id>` and `sys_connections_<id>` (`changed`), and `bx_messenger` (`convo_<id>`, `profile_<id>`).
- A profile's card follows a friendship or a follow without its list being requested again. UNA's reply to the action (`system/perform/TemplServiceConnections`) carries the profile's new `counts`; the buttons (`ui/molecules/objects/connections-ext.js`, `connections.js`) write them and their own new state into every cached list that holds the card (`applyConnectionPatch`, `lib/connection-cache.ts`; the rules and tests are in `lib/connection-patch.ts`). A change made elsewhere (another tab or device, the other person) arrives as the viewer's `sys_connections_<id>` event, which names both profiles: `Subscriber` then asks `system/get_card_state/TemplServiceConnections` for that one profile, only when a loaded list shows its card. Don't refetch a list to update a count. A list answer that was requested before the change would put the old state back, so a change is kept for ten seconds and written again over such an answer (`lib/patch-keeper.ts`); rows a list holds behind "Show New" show their newest copy (`lib/browse-query/held-rows.ts`). A profile's own page asks for its cover alone (`getPageData(url, false, {}, 'none')`, `components/page-layout/profile.js`) and replaces it. A count that changes in place shows it: `CountText` (`ui/atoms/count-text.tsx`, rules in `lib/count-change.ts`) rolls the number to the new one on web and holds the accent colour for a moment on every platform; put it inside a `Text` wherever a count can change while it is on screen.

### Images

Never pass an original upload (`src_orig`) to `Image` or `next/image`, on web or native. UNA transcodes images; NEO only resizes the display URL further.

1. Pick the URL with `pickUnaDisplaySrc` / `toUnaDisplayImageItem` from `app/lib/image-helpers` (`src`, then `medium`, `small`, `thumb`, `file`).
2. Render through `app/ui/atoms/image` only. Web uses `next/image`; native requests the same optimizer at `${native_app_images_url}/_next/image`.
3. Spreading a UNA object (`<Image {...image} />`) is safe because `getImageSrc` ignores `src_orig`. When you flatten a list, call `toUnaDisplayImageItem` so the original isn't copied into `src`.
4. `useOriginalImage` in the atom means "the optimizer request failed, use the UNA display URL", not `src_orig`.

## Code conventions

- Write new files in TypeScript (`.ts` / `.tsx`) with typed props. When you substantially rework a `.js` file, `git mv` it to TypeScript first so history follows.
- File names are kebab-case; shared prop types go in `<name>.types.ts`.
- Platform files: the base file is the native or shared version, `.web.*` replaces it on web, and `.ios.*` / `.android.*` hold platform-only native code. A platform pair shares props through `<name>.types.ts`; don't import types from the base file, because `./video` inside `video.web.tsx` resolves to `video.web.tsx` itself.
- `yarn typecheck` (`scripts/typecheck.js`) checks every `.ts` / `.tsx` file in `packages/app` and the apps once per platform, resolving `.web` / `.native` / `.ios` / `.android` the way webpack and Metro do. Plain `tsc` misses platform files, and JS isn't typechecked at all. The native run uses the root `tsconfig.json` with `strict`, `strictNullChecks` and `noUncheckedIndexedAccess`, so `items[0]` is possibly `undefined`.
- Keep these as JavaScript: `packages/app/settings/**` (config data read by string path through `appSetting`; `settings/images-allowlist.js` is also required by `next.config.js`), `packages/app/customization/**` (the fork surface), and `lib/image/circle-png.js`.
- Imports: shared code is `app/...`. Use `View`, `Pressable`, `ScrollView`, `Row` from `app/design/view`, `Text` and `H1`–`H6` from `app/design/typography`, controls from `app/design/controls`, `appSetting` and `isWeb` from `app/lib/util`. Don't import these primitives from `react-native` in shared code.
- Check for an existing component before writing one, and wrap a new third-party UI library in `ui/atoms` or `ui/molecules` before features use it.
- Lazy loading: `lib/lazy-component.tsx`, or `next/dynamic` (the Metro shim makes it work on native).

### React Compiler

The React Compiler is on in both apps: `reactCompiler: true` in `apps/next/next.config.js` (client bundle only) and `experiments.reactCompiler: true` in `apps/expo/app.config.js`. Shared code in `packages/app` is compiled by both.

- The compiler skips any component or hook that breaks the Rules of React and leaves it as written. `yarn lint` reports these as `react-hooks/*` errors (`refs`, `immutability`, `static-components`, `preserve-manual-memoization`, ...); fixing them is how a component gets compiled.
- Don't mass-remove `useMemo`, `useCallback` or `memo`: in a skipped component they still do their job. Drop manual memoization only in files that lint clean, and only when it serves no other purpose (a stable callback for a subscription, for example).
- `'use no memo'` at the top of a file or component body opts it out. A fork can turn the compiler off with `reactCompiler: false` in `customization/config/next.config.js` and `experiments: { reactCompiler: false }` in its `customization/config/app.config.js`.
- Code that mutates an object from props or state in place and expects children to re-render shows stale UI: memoized children see the same reference. Create new objects.
- Don't dispatch no-op state updates from effects (`setState(prev => prev)`). While a fiber still holds a low-priority update (idle hydration of the page `Suspense`, for example), React can't bail out early, and a no-op dispatch keeps a sync render loop going. See `MenuTop` in `components/nav/menu-top.tsx`.

### Icons

Render icons with `<Icon icon="House" />` from `app/ui/atoms/icon`, using Lucide names. Web draws them as CSS-mask SVGs from `/lucide/<stroke>/<Name>.svg` (generated by `apps/next/lib/generate-lucide-icons.js` from `lucide-static`); native uses `lucide-react-native` through the icon set. Never import `lucide-react`; it isn't installed. Animated icons: [animated-icons.md](animated-icons.md).

## Styling

- Design tokens (colours, radii, shadows) are the Tailwind `@theme inline` map in `packages/app/design/styles/theme.css`, with light and dark values in `palette.css`. `apps/next/tailwind.config.js` and `design/tailwind/theme.js` are not loaded by any build; a token added there does nothing.
- Settings hold class presets per component (`settings/theme/*.js`), read with `appSetting`. Use tokens and existing presets, not raw colours or arbitrary values.
- Neutral fills are translucent "ink", so they stack instead of blending: `bg-bubble` (comment bubbles), `bg-button` and `bg-button-hover` are the scheme's `--ink` at 4.5%, 8% and 12%; `bg-code`, behind code in native rich text, is 7%. A button on a bubble on a card is one even step darker than each layer below, and text keeps AA on every stack. `--ink` is `--neutral-950` in light and `--neutral-50` in dark (`palette-schemes.css`); the alphas are `color-mix()` in `theme.css`, one value for both schemes.
- Write an alpha only as `color-mix()` or an opacity modifier (`bg-button/50`). Uniwind compiles `rgb(var(--x) / 0.07)` and a variable holding `r g b / a` into `NaN` on native, so the colour silently disappears there.
- Native buttons read the same tokens through `theme.expo_ui.button` (`settings/theme/expo_ui.js`): iOS bordered (`tint`) and Android tonal take the translucent `bg-button`. Android's elevated button (the `glass` style) draws its shadow under the container, so it uses the opaque `bg-button-solid` (the legacy `--button`) instead.
- Edit the style partials in `design/styles/` (`theme.css`, `palette.css`, `utilities.css`, `global.css`), not `apps/expo/global.combined.css`, which only imports them for Uniwind.
- Variants: `web:`, `native:`, `ios:` and `android:` are defined in `design/styles/global.css`, as is `dark:`. Native switches themes with `Uniwind.setTheme`. For a JS value per theme, use `useThemeValue(light, dark)` from `app/design/theme`.
- Breakpoint tiers are mobile (no prefix), tablet (`sm:`) and desktop (`lg:`), as in `lib/responsive-classes.ts`; there is also `3xl:`. In code, `useScreenTier()`, `useIsDesktop()` and `useBreakpoint()` (`context/measure.ts`) switch at the same widths as the classes: on web they ask the browser's media queries (`lib/media-breakpoint.ts`), because the measured window width leaves out the scrollbar. Don't compare `useWindowWidth()` with a breakpoint yourself. Lists size by container queries (`@container/list`, `@list-sm/list:`).
- Cards, blocks, buttons and inputs draw their outline with a shadow (`shadow-card-outline`, `shadow-block-outline`, `shadow-btn-outline`, `shadow-input-outline`). Always pair it with the dark variant, `dark:shadow-*-deep`.
- Class names must be static strings or come from static mapping objects; Tailwind and Uniwind only see classes written out in scanned files.
- In files native scans, don't use CSS-variable colours inside `box-shadow`, and don't use `calc()` that mixes `%` with a length. Put those in web-only files.
- `withUniwind` is only for third-party components; core `View`, `Text`, `Pressable`, `Image` and `TextInput` take `className` already.
- Measure only when behaviour depends on rendered size, and then with `onLayout` (web emulates it in `design/view.web.tsx` with a `ResizeObserver` only for components that pass it). Avoid feature-level DOM measurement.

### Text styles on native

On React Native, text styles don't cascade from a `View` or `Pressable` to the `Text` inside. Put text classes on the `Text` itself:

```tsx
// Wrong: the text stays black on native
<Pressable className="text-muted-foreground"><Text>Label</Text></Pressable>

// Right
```

### Overflow and clipping

Outlines are shadows, and shadows paint outside the element box, so any clipping ancestor cuts them off (most visibly on the first and last grid columns).

- Blocks never clip. `BlockWrapper`, `Block` and `BlockContent` don't set `overflow-hidden`; `BlockWrapper`'s `clip` prop only works together with `fill`. Don't turn it on to hide a layout bug. (Blocks with `overlayHeader` are the exception.)
- Every web `ScrollView` clips both axes: `.neo-sv` is `overflow-y: auto; overflow-x: hidden`, and CSS can't scroll one axis and leave the other visible. Don't wrap block content in a `ScrollView`; page blocks already live inside the page scroller.
- Put `overflow-*` or a `ScrollView` on the one element that really scrolls or clips (a message list, a table, a fixed-height pane). For modals, use `<Modal scrollable>` instead of nesting a `ScrollView`.
- Give shadows room inside a scroller: pad the content and cancel the padding outside, for example `<ScrollView horizontal className="-mx-1" contentContainerClassName="px-1 py-1 gap-3">`.
- Clipping leaf elements is fine: rounded media (`rounded-xl overflow-hidden`), avatars, progress bars, `truncate`.

### Block design box per breakpoint

A block's chrome (background, padding, title) comes from UNA's `designbox_id`, which is one setting for every screen size. The block's App config (Studio → Developer → Pages → block → "Config (for App in JSON format)", sent as `config_api`) can set it per tier:

```json
{ "designbox": { "bg": ["tablet", "desktop"], "padding": ["mobile", "tablet", "desktop"], "title": ["desktop"], "rounded": ["tablet", "desktop"] } }
```

- Each key lists the tiers where that part shows: `mobile` (no prefix), `tablet` (`sm:`), `desktop` (`lg:`). `true` and `false` mean every tier or none.
- Corners without a `rounded` key follow the page: rounded where the page's padding keeps the block off the screen edge, square where the block meets it. The `default`, `login` and universal column layouts tell their blocks through `PageChromeProvider` (`ui/molecules/page/page-chrome.tsx`); in other layouts (home, profile, post ...) blocks keep `theme.blocks` `u-block-rounded-default` (square on phones).
- The background classes come from `lib/block-bg-classes.ts`; run its tests with `node --test packages/app/lib/block-bg-classes.test.ts`.
- A missing key takes the page's `designbox` (below), then `designbox_id`. Props passed from code (`showBg`, `showPadding`, `showTitle`) win over all of them.
- Keys sit under `designbox` because every `config_api` key is also spread into each element of the block as a prop.
- `components/block-wrapper.js` reads them and `ui/molecules/page/page-block.js` turns tiers into classes through `responsiveClasses`. Prefixed classes must stay listed in `@source inline(...)` in `design/styles/utilities.css`; update that list if `theme.blocks` `u-block-bg` or the block padding changes.
- Studio's "Padding" and "Title size" (Studio → Pages → block: Regular, Compact, Large) size the block's padding and its title, on the site and in the apps. UNA sends them as `padding_size` and `title_size` (`''`, `compact`, `large`; `''` for a design box without that part).
  - Padding: `PageBlock` and its parts take it as `padSize` and use the sized `theme.blocks` keys `u-block-pad-{x,y}-compact` (8px) and `-large` (24px), with `u-block-gap-compact` / `-large` in place of the gap in `u-block-base`, so the space between the title and the content follows it as on the site. The tier presets are `block-pad-{x,y}-{compact,large}` in `lib/responsive-classes.ts`.
  - Title: `BlockTitle` and `BlockTitleStacked` take it as `titleSize` and use `u-block-title-compact` / `-large` and `u-block-title-stacked-compact` / `-large`: `text-base leading-6` (compact) or `text-2xl leading-8` (large) instead of the regular `text-xl leading-7`. Over a description they sit on 20px, 24px and 32px lines, and the header icon follows the size (44, 48, 56px), so it stays as tall as the title, the gap and one line of the description.
  - A theme without the sized keys keeps the regular padding and title. Run the tests with `node --test packages/app/lib/block-size.test.ts`.
- List (browse) blocks skip `BlockWrapper`. The list endpoint carries their `designbox`, and `paddingForList` (`default/functions.js`) turns `bg` / `rounded` into a card around the list. The card has no padding of its own (its items space themselves), so "Padding" and "Padding hidden on" don't apply to it. This is web only: a native list scrolls under the overlaid page header.
- Use this rather than per-page or per-block overrides in code: block ids and pages differ between UNA sites.

The page's App config (Studio → Developer → Pages → page → "Config (for App in JSON format)", sent as `config`) sets the page around its blocks, with the same tiers:

```json
{ "padding": ["tablet", "desktop"], "gap": true, "designbox": { "bg": ["tablet", "desktop"], "padding": ["tablet", "desktop"] } }
```

- `padding` and `gap` are the page content's padding and the gap between its blocks (`layout.page_content_padding` / `page_content_gap`; unset uses `page_content_padding_default`, `page_content_padding_layouts` and `page_content_gap_default`).
- `designbox` is the default for every block on the page, browse lists included (the card `paddingForList` draws around them); a block's own keys win, key by key. It applies to every block with a design box, so leave out keys that only some blocks should take. `"rounded": false` means square everywhere.
- Examples: margins everywhere with rounded cards needs nothing (the default). Content without a card on phones: `{"designbox": {"bg": ["tablet", "desktop"], "padding": ["tablet", "desktop"]}}`. Edge-to-edge square cards on phones, rounded cards with margins from tablet: `{"padding": ["tablet", "desktop"]}`.
- A fork sets the same keys for a page URI in `layouts[<uri>]` of `customization/settings.js`, used when UNA sends no page config.

### Fonts

Text uses two roles, `font-main` (the default in `design/typography.tsx`) and `font-title` (headings). Pick the family per role and platform in `customization/config/fonts.js` (defaults in `design/fonts/font-config.js`), for example `main: { web: 'inter', ios: 'system', android: 'inter' }`.

- `'system'` is the platform UI font: SF Pro on iOS, the device sans-serif on Android, the OS font stack on web (the same stack as UNA's, in `global.web.css`). It is the default for every role and platform, so stock NEO loads no font file. Keep it that way upstream; custom fonts are a fork's choice.
- Any other value is a key of `design/fonts/font-families.js` (`'inter'`; its files ship in `design/fonts/`). Native needs one static file per weight (iOS and Android pick the face by `fontWeight`; variable fonts don't work). Web needs a `next/font` instance per role, created in `customization/design/fonts/fonts-web.js` and passed to `webFontClassName()`; core creates none (example in `design/fonts/fonts-web.web.ts`).
- A fork adds its own font under `families` in `customization/config/fonts.js`: the same shape as `font-families.js`, with the static files under `packages/app/customization/` and `native` paths relative to that folder (example in `font-config.js`). Select its key for `ios` and `android`, and load it on web in `customization/design/fonts/fonts-web.js`. Run the font tests with `node --test apps/expo/plugins/with-app-fonts.test.ts`.
- iOS and Android values are build settings: `apps/expo/plugins/with-app-fonts.js` embeds only the selected families, so changing them needs a prebuild and a native rebuild. At runtime `design/fonts/native-fonts.ts` points the Uniwind font variables and the navigation header fonts at the family.
- Don't set `fontFamily` inline; use `font-main` / `font-title`. Expo UI (SwiftUI / Compose) views are the exception and take `nativeFonts.main`.

## Components

### Buttons

Use `NeoButton`, `NeoButtonLink` or `NeoButtonRef` from `app/design/controls`. The legacy `Button`, `ButtonRef` and `ButtonLink` are deprecated.

- The `bordered` look is shared with UNA's regular buttons and header toolbar (`template/css/tailwind.css`): `bg-button` at rest, `bg-button-hover` on hover and press (the button scales to 98% instead, 110% under a finger), the label and icon `text-button-foreground` (neutral-700, 300 in dark) turning `text-button-foreground-hover` (neutral-900, 100 in dark) on hover, and the accent colours (`bg-accent`, `text-accent-foreground`) while its menu is open (`selected`). UNA keys that on the trigger's `aria-expanded="true"`. Change both together; `BxBaseMenuToolbarTest` checks the values match.
- Axes: `style` (`plain`, `bordered`, `borderedProminent`, `borderless`, `outline`, `link`, `text`, `glass`, `glassProminent`; `text` is a quiet JS-only text link, as in the footer), `role` (`default`, `cancel`, `close`, `confirm`, `destructive`), `controlSize` (`mini`, `small`, `regular`, `large`, `xlarge`), `borderShape` and `tint`.
- Code lives in `design/controls/neo-button/`: props in `neo-button.types.ts`, scope and style precedence in `neo-button-resolver.tsx`, the legacy variant mapping in `control-scale.ts`. The theme is `neo_button` in `settings/theme/buttons.js`.
- On iOS and Android, `native.expo_ui_buttons` (`settings/configs.js`) renders buttons with native Expo UI (SwiftUI / Compose) views; the `expoUI` prop controls it per button.
- `NeoButtonGroup` joins buttons into one control with the same `style`, `controlSize`, `borderShape`, `role` / `tint` and `width` axes. The group paints the style's surface once (no border: outline and glass are shadow rings); each NeoButton inside becomes a segment through context, with the group's style and size, only the state washes, square inner corners and no hit area over its neighbours. Segments always use the JS surface; a `glass` group on iOS 26+ draws native liquid glass behind them. Recipes are `neo_button.group` in `settings/theme/buttons.js`. Object menus (reactions, likes, scores) build theirs through `ButtonsGroupMenu`, which uses `group.defaultStyle`.
- `/pg` is a playground for every axis (`apps/next/app/pg/page.js`, `apps/expo/app/pg/`). It isn't gated, so production builds serve it too.

### Menu labels

Every menu's labels are the same in NEO and UNA: 14px on a 20px line, medium (500), normal tracking; `text-secondary-foreground` at rest (gray-600, gray-400 in dark), `text-foreground` on hover, `text-accent-foreground` for the current item (blue-700, blue-300 in dark). That covers the main menu and its More rows, a section's subtabs (`menu-items/submenu.js`, which sets `font-medium` over NeoButton's semibold: tabs are navigation, not actions), dropdown rows (`dropdown_menu.item_text`, the footer's language, theme and sounds switchers among them) and the home menu grid. UNA's popup rows (`.bx-popup ... .bx-stl-mit` in `template/css/tailwind.css`) and current subtab (`.bx-menu-main-submenu`) match. Buttons keep semibold.

### Menu button style and size

UNA says per menu how its buttons look and how big they are: Studio > Navigation > a menu > "Button style" (Automatic, Regular, Glass, Plain) and "Button size" (Automatic, Mini, Small, Regular, Large). The menu's API carries them as `button_style` and `button_size` (empty for Automatic).

- `components/menu.js` fills them into the menu's `params` with `withMenuButtonParams` (`lib/util/menu.ts`): `regular` is NeoButton `bordered`, `glass` is `glass`, `plain` is `plain`; the sizes are NeoButton's control sizes of the same names.
- They are the default, not an override: a call site that passes `button_style`, the legacy `button_variant` or `button_size` keeps its own. To let UNA decide for a menu, leave those out at the call site.
- A call site that needs a look for a menu UNA leaves on Automatic passes `button_style_default` / `button_size_default` instead: UNA's choice wins over them, and they apply when UNA has none. The order is fixed value, UNA, default (`lib/menu-button-params.ts`, with tests).
- A menu that still draws its buttons through the legacy adapter passes `button_variant_default` (a legacy variant) as its default look.
- UNA's style is set as `button_style` and also as `button_variant`, because the items drawn by the legacy adapter (likes, favorites, reports and the like) read only the variant. The adapter and `ButtonsGroupMenu` take a NeoButton style name there.
- Menus that follow UNA this way, with their defaults for Automatic:
  - the cover's actions (`CoverMenu`, `CoverMenuMore` in `components/elements/covers/menu-cover.js`): glass on phone and tablet, where the actions sit over the cover picture, bordered on desktop;
  - a content page's actions (`components/elements/entity-actions.js`): the legacy default variant (bordered), small;
  - the action button of a people or groups card (`UnitRecommendation` in `components/units/helpers.js`), from the card's snippet meta menu: borderless, small.
- Glass is for a menu over a picture or another backdrop that varies (a cover, a header without chrome). Prefer setting it on the menu in UNA over hard-coding `glass` at a call site, so the site and the apps agree.

### Form labels

UNA picks how forms label their text fields: above the field (regular, the default) or floating inside it (adaptive). It is one setting for the site and the apps, Studio > Designer > Settings, and a form display can have its own (Studio > Forms > Displays). Every form's API carries the resolved style as `params.label_style`.

- `Form` passes it to each field as `label_style`; `hasAdaptiveLabel` (`lib/form/label-style.ts`) floats the label only for field types that can (text, password, phone, embed). Every other field, and every form of a UNA that sends no style, shows regular labels.
- `forms.adaptive_labels` overrides UNA for the whole app: `null` follows UNA, `false` never floats labels, `true` always does. `forms.without_captions` (empty by default) lists forms that show captions as placeholders instead of labels.
- Required marks follow UNA too (`params.required_mark`, "mark the fewer"): `none` when every labelled field is required or none is (login, sign-up), `optional` puts "(optional)" on the optional fields, `required` puts the `forms.mandatory_icon` on the required ones. A UNA that sends no mode keeps the icon. `forms.optional_text` replaces the word "optional".
- The sign-in form's "Forgot password?" is drawn by the Password field (`forms.sys_login.forgot_password_link`, `fieldLink` on `Field`): at the end of the label's line, or under the field (on the description's line) when the label floats. On web it comes after the input in the page and is ordered before it (CSS `order` in a wrapping row), as on the site, so Tab goes Email, Password, Show password, the link; no `tabIndex`. Emptied, `AuthPanel` shows the centred link under the form again.
- A label above its field is `forms.caption_classes`: 14px medium in neutral-700 (neutral-300 in dark), the site's `.bx-form-caption`. `tests/units/template/SignInBlockParityTest.php` reads both.

### Block header

### Interface sounds

Sounds are [Cuelume](https://cuelume.dev/agents.md)'s cues, one per interface job. Pick a cue by its job from Cuelume's "Which cue?" table: subtle emphasis for frequent actions, strong only for rare ones that matter. Never play one on hover, on page load, per item of a burst, or for a number that updates constantly. Everything is in `app/lib/sound`.

- Web synthesizes cues with the `cuelume` package. `InterfaceSounds` (`ui/molecules/system/interface-sounds.tsx`, mounted once in `apps/next/app/providers.js` and `components/nav/tabs/index.js`) calls `bind()` and applies the settings.
- Native plays WAV files rendered from the same package version, in each of Cuelume's four sets (themes): `Sounds` in `default/sounds.js`, keyed `[<set>-]<cue>[-<emphasis>][-back]` (the default set has no prefix); the files are in `packages/app/resources/sounds/`. A cue without its own key falls back to a plainer key, then to the default set's, then to the pre-Cuelume key for its job (`click`, `tab`, `success`, `notif`). After bumping `cuelume` (pinned in `package.json`), or to give native a new variant, add it to `CUES` in `scripts/render-sounds.mjs`, run `node scripts/render-sounds.mjs` (needs Chrome; mono 32 kHz, every set) and add the keys to `default/sounds.js`.
- A press: `cueAttributes(cue)` on the pressed element (web; `bind()` plays it as the pointer goes down) plus `playPressCue(cue)` in the handler (native). NeoButton has a `sound` prop: by default a button with haptics taps (subtle unless prominent), a menu trigger opens or closes, `close` / `cancel` roles close. `PressCueContext` changes the cue for the buttons inside (menu items select). Native buttons answer with haptics only; native plays cues for toggles, disclosures, the tab bar and outcomes.
- An outcome: `playCue('success', { emphasis: 'subtle' })` once UNA has saved, `playCue('error')` when it refuses. `Form` already does this for every submit with a reply (not for filters or save-on-change forms).
- Kinds of action: UNA's settings can give buttons, choices, reactions, menus, navigation, results and notifications their own set, or no sound. A cue's kind comes from the cue (`cueGroup` in `lib/sound/cues.ts`); a like, reaction, rating, favorite or follow plays `toggle` with `group: 'reactions'` (`cueAttributes` turns that into `data-bx-sound-group`).
- Settings: UNA's Studio > Settings > Global > Sounds (`BxDolSounds`) picks where sounds play (`neo_web`, `ios`, `android`), the set, the volume, the level people start at and the set per kind of action. They come with every page as `data.sounds`; `Layouts` passes them to `applySoundConfig` (`lib/sound/config.ts`), which keeps them in memory and storage. Sounds only read that copy, so nothing waits on a request, and changes apply from the next page. On web, a capture listener (`gatePress` in `sound.web.ts`) gives each press its kind's set or silence before `bind()` plays it.
- Users pick their own level, full, quiet (40%) or off (`useSoundsLevel`, in the footer and the dashboard settings), stored as `layoutSettings.sounds`; unset follows UNA's starting level. `layout.sounds` turns sounds off for the whole build. Native interface sounds follow the iOS silent switch.
- `useSound` / `playSound` with the old names still work; they play the cue for that job.

### Push notifications

Push goes through a provider in `app/lib/push`: an object with `isConfigured`, `permission`, `prepare`, `requestPermission`, `login` and `logout` (`types.ts`). OneSignal (`onesignal.ts` / `.web.ts`, app id from `config.api_keys.onesignal`) is the only one so far; `notifications.push_provider` picks one by its key in `pushProviders`, and `''` turns push off. Only `lib/push/onesignal*` imports OneSignal's SDK, apart from the deprecated `subscribeOneSignal` (`lib/util/misc.ts`), kept for projects that call it from `customization/`.

- NEO asks with its own dialog, the `push_prompt` molecule (`ui/molecules/system/push-prompt.tsx`, mounted by `push-prompt-host.tsx` in both layouts), never a provider's UI: OneSignal's slidedown and welcome notification are off, because they show the icon and wording from OneSignal's dashboard.
- The dialog shows `notifications.push_prompt_delay_ms` (two minutes) after a member's first page of a run (a web tab, a native launch; the web layout mounts again on every page, so the delay is counted from the first one, `pushPromptWaitMs`), once per run, only while the system can still ask (`permission()` is `default`). "Turn on" calls `requestPermission()` straight from the press (browsers drop a request that isn't part of a gesture, so `prepare()` loads the SDK before the dialog opens), then links the device (`linkPushMember`, once per run). "Not now", Escape, a press outside, and a system request that ends without a yes all keep it away for `push_prompt_snooze_days` on that device. A member who already allowed notifications is linked quietly. `push_prompt: false` never asks. The rules are in `lib/push/prompt-rules.ts`; run their tests with `node --test packages/app/lib/push/prompt-rules.test.ts`.
- A new provider implements `PushProvider`. Core's go in `pushProvidersDefault` (`lib/push/providers.ts`); a fork adds its own in `customization/push.js`, which re-exports that map, and names it in `notifications.push_provider`. Don't register one from `customization/settings.js`: the server reads the settings, and `app/lib/push` is client code. A fork can replace the dialog through `push_prompt` in `customization/molecules/_map.js`.
- The older `notifications.onesignal_prompt_delay_ms` and `onesignal_request_on_load` (`notifications` or `native`; `false` turns the dialog off) still apply where a fork sets them.
- Sign-out calls `logoutPush()` (`lib/platform/session-cleanup.ts`), so the next account isn't sent the previous one's notifications. The same cleanup runs when a session starts, so a provider's `logout()` must be cheap when nothing is linked; OneSignal's only unlinks once its SDK is loaded in this run. A link belongs to the session it was asked for in (`pushSession()`, passed to `linkPushMember`): once that session has ended it is dropped, and an unlink waits for a link already on its way (`lib/push/sessions.ts`, with tests), so a member who answers the system's request after signing out is not linked again.

### Page header

The page header is mounted once per `Layout` (`ui/molecules/header/page-header.js` / `.web.js`). A page never writes header state from an effect; it declares what it needs in its render tree with `PageHeaderOptions` from `app/ui/molecules/header/options`:

```tsx
<PageHeaderOptions sub={subHeader} mobileOnly />   // sub row on mobile only (feed switcher, tab bar)
<PageHeaderOptions backButton title="Post" />      // item page
<PageHeaderOptions main={<MobileChatHeader />} /> // replace the whole bar
<PageHeaderOptions main={bar} ownBackButton />    // the bar draws its own Back (native adds none)
<PageHeaderOptions actions={actions} />            // header actions
<PageHeaderOptions hidden />                       // no header (a cover owns the top)
<PageHeaderOptions band />                         // band behind the bar on mobile (feed); off by default
<PageHeaderOptions showTitle={false} />            // no title on mobile (the page draws its own heading)
```

The header has three states, matching UNA's three tiers (phone, tablet from `sm`, desktop from `lg`):

- Phone: floating buttons; the logo mark where there is no bottom tab bar (guests) and on Home; the page title, after the section's icon on a section's page (`SectionIcon`, `ui/molecules/section-icon.tsx`), where the page's cover is on for this viewer (Studio → Pages → page → Cover: all, visitors only or members only; UNA sends it as `cover`). A page that passes `title` always shows it; `showTitle` overrides both. A top-level page without a section menu that the tab bar leads to (Messenger) takes its tab's icon (`useSectionIcon`). Pages keep this shared header and add to it with `PageHeaderOptions` (`title`, `actions` in place of the site toolbar, `sub` for the row under it, as Messenger's list does); only a screen with its own Back and title (the open chat) replaces the bar with `main`.
- Tablet: floating buttons and the full logo, otherwise as on phones: the title (with a section's icon) in the header row, the conductor's tabs on the second row, a section's actions and tools (Add, Search) at its end.
- Desktop: the full header with the site menu. Conductor pages (a section: pages that share a sub-menu, `navigator`) keep the section's tabs above the content, as the site does, laid out as a compact profile cover (`TopSidebar`): a first line (the 64px strip of a compact cover) with the section's icon (`SectionIcon`: the icon the main menu draws for the section, its site-menu item, else the tab bar's (Dashboard, Friends, Notifications), `lib/section-icon.ts` with tests; animated, 32px in a plain 44px box), its name (the page heading) and its actions (Add...), a second line with the tabs and the section's tools (filters, Search) at its end, both pinned under the header with the header's chrome (`conductor.cover_bar`: `bg-card/60` over a blur on web, and `cover_bar_edge`: its `shadow-border-b`; a profile's cover bars use the same), unless the section's menu asks for a sidebar: then the section title and nav go in the left column (from `lg`, `hide_top_menu_from` and the `cols-l-c` / `cols-l-c-r` left `breakpoint`) and the tab row hides. UNA says it per menu, Studio > Navigation > a menu > "Section navigation in the apps" (Tabs / Sidebar), sent as the menu's `section_nav` (`getMenuSectionNav` in `lib/util/menu.ts`; the connections' menu has the sidebar). A UNA that sends none keeps the sidebar (`menu_items.section_nav_default`, or `menu_items[<object>].section_nav`). Profiles keep their tabs either way, and native always shows tabs. Regular pages show the cover title above their blocks (`PageTitle` in the `default` and universal layouts).
- A section can open on its own menu on phones and tablets instead of tabs: Studio > Navigation > a menu > "Section navigation in the apps on phones and tablets" (Tabs / List), sent as the menu's `section_nav_small` (`isMenuSectionList` in `lib/util/menu.ts`; the account's Settings have the list). The list is at the section's own page, the uri the menu names in its App config (`hub`: `settings`; a menu without one keeps tabs). UNA sends that page with no blocks and it is none of the menu's items: `fillTabs` marks its route `sectionRoot` (no tab) and gives it the menu as its one block (`lib/section-list.ts`, with tests), drawn by the menu element (cards in sections, `settings-menu.tsx`). The sections are the menu's own structure (Studio > Navigation > the menu's items, an item's Parent): a top-level item without a link that has subitems heads a section with its title (Settings: "Account", and the current profile, titled `{member_display_name}`, which UNA fills with the profile's name); the items outside them make a section without a heading, and an item whose App config says `"danger": true` (deleting the account) is a section of its own in the destructive colour. `getMenuSectionListItems` (`lib/util/menu.ts`) lifts the section parents out before `fillTabs` makes the routes, each subitem marked with its `section`, so the routes, the first page and the titles see one flat list, as UNA's site shows its tab row; `lib/menu-sections.ts` (with tests) builds the sections from it, and the desktop sidebar draws the same ones (`SidebarNavSections` in the conductor's `web-ui.js`). An older UNA sent a group per item instead (`group`, or the `group` key of its `config`: `account`, `profile`, `danger`), which still makes the sections in that order. Below desktop the tab row is gone, each page opens from the list with the header's Back and is titled by its item. On desktop, and where the menu is on tabs, the section's own page opens the menu's first tab (`isConductorRouteLeft`; hidden meanwhile, so the list doesn't flash), as UNA's site redirects it. An older UNA, where the page is an item of the menu ("Overview", hidden on desktop) with a menu block, works as before.
- The desktop site menu (`components/nav/menu-top.tsx`) works as UNA's main menu (`BxDolMenuMoreAuto`): every tab keeps its icon and label, the tabs that fit stay in the bar in order and from the first that doesn't, the rest go to the top of More (`lib/navbar-fit.ts`, with tests). The site menu's "Persistent items" (Studio > Navigation, sent as `persistent`) never go under More; `menu_items.menu_navbar_site_tabs` is an optional upper limit (0: as many as fit). Each tab's width comes from a hidden copy of the bar that repeats the tab's classes (`components/menu-items/topmenu.tsx`), so change them together. The current tab is filled as on UNA's site (accent-200/accent-900 at 60%, sliding from tab to tab); its place is worked out from the measured widths of the row and where it starts (`navbarRowStart`, `navbarTabBox`), not from each tab's own layout events, which miss a tab that moves without changing size; when the current page's tab is under More, More takes it. More holds only the site menu's items that don't fit, as on UNA's site; `layout.apps_in_more` (off by default) also lists the launcher's apps there. Tabs have a regular button's 12px corners and a 14px medium label. Header popups (More, Add, notifications, the account menu) open under their buttons, lined up with the button's end edge on the right half of the window (`DropdownMenu align="auto"`), and More is one list; More's rows are drawn as tabs too (`DropdownMenu plainIcons`: a 24px icon without a circle, the same label, hover and press, and the current page's row, `current`, in accent-200/accent-900 at 60%), as UNA's More list (Artificer `tailwind.css`, `.bx-menu-submenu-more-auto`; `ArtificerMenuRowsTest` keeps them together). The header menu below `lg` (`menu_navigation`, `components/nav/menu-header-navigation.tsx`) draws the same rows (`plainIcons`, the current page's row marked from `url` / `uri`), as UNA's main menu dropdown below `lg` (Artificer `sidebar_site.html`, `#bx-sidebar-site` in `tailwind.css`).

- The desktop header's width and the main menu's place follow UNA's Designer (Studio > Designer > Settings > Header), set per page layout and audience: Standard pages and Application pages each have a header for visitors and one for members, each with a width (`page`: as wide as the page's content, `full`: the window) and a place for the menu (`start`: next to the logo, `center`, `end`: next to the toolbar). So guests can get a page-width site with links next to the logo while members get full-width centred tabs on the same layout. Which layout a page has comes from the page (Studio > Pages, its type) or, for Default, from the visitors' and members' layouts in Designer. UNA resolves the header for the viewer and sends the result with every page as `header` (`{layout, width, align}`, `BxDolTemplate::getHeaderLayout`); `PageHeaderBody` reads it through `resolveHeaderLayout` (`lib/header-layout.ts`, with tests), keeping the previous page's header while a page has none, and an older UNA's pages get the old look (full width, centred). `layout.header.width` / `align` override UNA for the app (null follows it); `content_width`, `content_left_align`, `content_right_align` and `content_center_align` hold the classes.
- The main menu's bar is laid out by CSS alone, so what loads and what it replaces stand in the same place. The bar (`layout.header.content_center`) is as wide as all its tabs, up to `layout.header.menu_max_width` (800px; `null` for no limit) and to the room between the logo and the toolbar. The fit counts with that width, so with the limit the menu no longer fills the header: tabs that don't fit in it go under More. In the middle both sides of the header grow (`flex-1` with `min-w-max`, `content_left_align` / `content_right_align`): they are equal while the header has room for the bar between them, which centres the bar on the header; when it has not, the wider side keeps its content, the other takes the rest, and the bar fills what is left, its row in its middle. `start` and `end` grow one side only. Nothing measures the header to place the row: don't add padding or a transform for that. UNA's site still moves its row towards the header's middle inside a bar that is off-centre (`BxDolMenuMoreAuto::_balance`), and Artificer's settings can override Designer for the site only (Header width, Main menu alignment).
- Loading states of the desktop header (keep them when you change it):
  - Before the fit is measured (a visitor's server HTML until hydration) the bar holds every tab in a row that wraps and shows its first line only (`overflow-y: clip`). Each tab keeps More's room after it and the next takes it back (`me-13` / `-ms-13`: 52px, the gap plus More), so the line breaks exactly where the fit puts More (`navbarUnfittedTabSide` in `lib/navbar-fit.ts`; a test checks the two agree): the tabs are the ones the fit keeps, in the same place, and only More is missing until the page hydrates. The bar and the hidden copy report their first layout before the first paint (`layoutBeforePaint` on `View` / `Row`, `design/view.web.tsx`: an `onLayout` that answers before the browser paints, for an element whose first paint depends on its own size; every other `onLayout` answers after it), so a member (whose header only the client draws) never sees that state.
  - Placeholders show only the first time a member loads the site on a device: `useMenuData(object, { rememberFor: menuViewerKey(currentUser) })` (`context/menu-data.ts`, rules and tests in `lib/menu-remember.ts`) keeps the member's menu in localStorage (`neo:v1:menu-<object>`, one copy, with its viewer), draws it at once on the next load and replaces it when UNA answers. Another viewer's copy is dropped, also when the member signs out, and only a menu that arrived for the viewer is kept: one loaded before the viewer changed without a page load (signing in, switching the profile) stays the other viewer's (`isMenuOf`). Use it only for menus the server never renders for that viewer (the header's site menu, Add and Apps): the copy is read in the first render.
  - The placeholders are pills in the same bar, the same wrapping row clipped to its first line, so none is drawn over the logo or the toolbar.
  - The tab component (`menu-items/topmenu.tsx`) is imported statically in `components/menu-items/_map.js`: as a `next/dynamic` chunk it left the bar empty between the placeholders and the tabs.
  - The toolbar's buttons are 8px apart (`gap-2`), as in UNA's site toolbar (Artificer `menu_toolbar.html`); a page's own header actions that stand in for it (Messenger's list) too.
  - On the web a toolbar slot whose data is still loading (`ui/molecules/header/header-element.js`: Add and Apps until their menu arrives, a visitor's Search, Log In and Sign Up when their toolbar did not come with the page) draws a placeholder the size of its button (a labelled button is drawn hidden inside it, so the slot has that button's width in any language) and gives the slot up only when the data says it is empty, so the toolbar is as wide from its first paint as it will be. The menu fits its tabs in the room the toolbar leaves.
  - A member's page has no header in the server's HTML: the page waits for the viewer on the client.
- The page's width on the web follows UNA's Designer too (Studio > Designer > Settings > Page and header), per page layout and audience: pixels, or `full`. UNA sends it with every page as `page_width` (`BxDolTemplate::getPageWidth`); `PageWidthStyle` (`ui/molecules/page/page-width-style.web.js`, rendered by the page layout, `components/layouts.js`) puts it on `:root` as `--neo-page-width` through `resolvePageWidth` (`lib/header-layout.ts`, with tests), and `--container-8xl` reads it on the web (`design/styles/global.css`), so every `max-w-8xl` (page content, blocks, the header at Page width) follows. A page without one keeps the previous page's; before any, and on native, it is the theme's 1440px. `layout.page_width` overrides UNA (null follows it; a CSS length or `full`). The site sets the same width as `--bx-page-width` on `<body>`.
- The site footer's width on the web follows UNA's Designer too (the same table, "Footer width"), per page layout and audience: `page` (as wide as the page's content, its separator included) or `full` (the window, the separator from edge to edge). At `page` the box is `max-w-8xl` with the page's 16px sides from `lg`, so the separator and the links end where the header's row does at Page width; phones and tablets keep the footer across the screen.

- Application pages have a sidebar on the web, for members: UNA's Application layout (`header.layout: 'application'`, `resolvePageLayout` in `lib/header-layout.ts`; `layout.page_layout` overrides it, null follows UNA). `AppSidebar` (`ui/molecules/sidebar/app-sidebar.web.tsx`, mounted by `components/layout.web.js`) holds the logo with Search and Add on its first row, the context selector where the header would show one, UNA's panel menu (`menus.objects.panel`, `sys_site_panel`; an item without a link that has items is a group under a title that opens and closes, kept in `prefs.sidebarCollapsed`) and the member's account at the foot (`MenuAccount` with the profile switcher). From 1280px the header is a bare 16px strip in the page's colour, the sidebar the left column under it, outside the content, and the content one block (the blocks' surface, edge and corners) 16px from the window's other edges. The window still scrolls the page: the block's surface (`neo-app-frame`) is fixed behind it and its edge (`neo-app-frame-edge`) over it, with the page's colour spread around it, which hides what scrolls past (`design/styles/global.web.css`, "Application sidebar"). The sidebar is 16rem, or the width its edge was dragged to (240px to 400px, `prefs.sidebarWidth`), or a 4rem strip of icons with the logo's mark (`prefs.sidebarNarrow`); both are applied before paint (`data-neo-sidebar` and `--neo-sidebar-width-expanded` on `<html>`). Its edge is a handle: dragged it sizes the sidebar and snaps to the strip under 160px, pressed (or Enter, Space) it narrows or widens it, the arrow keys size it. UNA's site draws the same layout (Artificer `pt_application.html`, `css/common.css` "Application", `js/sidebar.js`); change both together.

A member's menu: their profile and the profile switcher, then UNA's site panel menu (`menus.objects.panel`, `sys_site_panel`), each item of which is another menu under its title (the profile's pages, the followed, the modules, the account's menu with Settings and Log out, the footer's links; a titled menu can be closed, a long one starts closed), then the Preferences (language, theme, sounds: `app-sidebar-prefs.ts`, the footer's rules). It stands outside the tabs, so the focused page reports its URL (`components/layout.js` → `context/app-sidebar`).

Only passed props take part in the merge. Mount registers, unmount removes, a prop change updates: gate with JSX or `mobileOnly`, not with `useEffect` / `useFocusEffect`. Only the measured height flows back, through `useHeaderHeight()` (`context/jotai/layout.ts`).

### Guest splash

What a guest sees on the home page is set in UNA, in Studio > Designer > Splash: one switch for the site and one for each app (web, iOS, Android), a shared code field and an optional code field per app. The guest splash is not the launch screen, the static OS screen iOS and Android show before JS runs (expo-splash-screen, `resources/native/`, Studio > Designer > Icon).

- The page request already says which app asks (`X-Neo-Platform`; anything else counts as web). For a guest on `home` whose app has the switch on, UNA sends `layout: 'splash'` and `splash: { source: 'una', code }` (`BxDolSplash`, `BxBasePage::getPageAPI`). `code` is the app's own code, else the shared code, and is left out when both are empty. A switch never saved follows the older `sys_api_root_page_guest` option. With the switch off, the guest home draws its Page builder blocks.
- `isSplashPage` (`lib/util/layout.ts`) picks the splash; `components.molecule.splash` (`ui/molecules/sections/splash.tsx`) draws it, first match wins: a project's own splash (that molecule replaced in `customization/molecules/_map.js`, or its own `splash_text` in `customization/static.js`), then UNA's code (`una-splash.tsx` / `.web.tsx`), then the built-in splash (`splash_text` plus the sign-in form).
- UNA turns its site markers into placeholders, `<neo-slot name="..."></neo-slot>`, which the apps draw with their own components (`splash-parts.tsx`): `login_form` (`__login_form__`, `__login_form_in_box__`: the sign-in form block, Forgot password, the social sign-in buttons and the Sign up link, as the built-in splash shows them), `social_login` (the social buttons alone; no marker, write the element), `join_link` (`__join_form__`, `__join_form_in_box__`: the "Create account" row), `logo` (`__logo__`), `illustration` (`__illustration__`: `Illustration name="splash"`) and `site_title` (`{site_title}` in text: the slot holds UNA's site name, which the apps show as text). `__join_link__` and `__login_link__` become `/create-account` and `/login`.
- UNA also runs the macros, removes scripts, inline event handlers, `javascript:` links and every element with a `data-site-only` attribute (parts for the site only; the site shows the splash between its own header and footer, as the apps do), and turns `<main>` into `<div>`: the apps have their own landmark. `lib/splash/splash-html.ts` parses the code, removes the same things again and splits it into runs of plain HTML and placeholders.
- Web renders the code as it is, `<style>` included, in `.neo-splash` between NEO's header and footer, in a box as wide as the page (`max-w-8xl`, with the page's 16px sides), as the site shows the splash inside its page: the code's own widths (the default's `88rem`) never pass the header's row at Page width, and text without a colour of its own takes the page's text colour (`text-secondary-foreground` on `.neo-splash`, the site's gray-600 / gray-400); elements that hold a placeholder become React elements (one that allows only inline content, such as a paragraph or heading, is drawn as a `div`, since the placeholders are blocks), the HTML between them goes in as markup, so server and client render the same. Links to the app's pages open in the app.
- iOS and Android render no web view. Text goes through the rich text renderer (`Html`, react-native-enriched-html): headings (a heading of text only is NEO's own `H1`–`H6`), paragraphs, lists, quotes, links, bold, italic, underline, strike-through and line breaks, aligned by `text-align` in `style` or an unprefixed `text-left` / `text-center` / `text-right` / `text-start` / `text-end` class on the element or one around it. An element with a placeholder inside is a centred column. Everything else is left out: `<style>` and layout CSS, `<svg>`, images, forms and iframes; other containers keep their text. Use the per-app code field for an app that needs different code.
- Native keeps the last guest splash it showed (`lib/cache/guest-splash-cache.ts`, from `components/nav/expo-screen.js`). At the next launch, once the tabs bootstrap knows the viewer is a guest (`currentUser === false`), the home tab shows it while the home page loads. Any page that comes back for a member drops it, and member tabs never read it.
- UNA's default code (`sys_site_splash_code`) looks like the built-in splash in every app, so a fresh install looks the same until an operator edits it.
- The splash's sign-in form is UNA's sign-in block (`system:login_form`), found in the page's blocks. The guest home's sign-in, join and forgot password blocks are off for the apps as installed; UNA still sends them to a guest's home (`BxDolSplash::AUTH_BLOCKS`), marked `splash_only: true`, so every splash finds them (also one a project forces with `layout.use_splash_page`) and the home layout leaves them out. A block that is on for the apps comes without the mark and shows on the home page.
- The sign-in block's padding is the home page's block's (Studio > Pages > Home > the block > Padding, large as installed), sent as `padding_size` like any block's; UNA's site sizes the box of its splash's form from the same row (`BxDolSplash::getFormInBox`), so one setting sizes both.
- Without the splash the guest home draws its blocks and, above them, UNA's home cover (`cover_home`: title, `title_accent`, text, the picture from Studio (the page's cover, else Designer's common cover) or else the template's art (`image_default`, light and dark), Sign up and Log in for guests with their icons; `components/elements/covers/home-cover.tsx`) where the site shows it: covers on in Studio > Designer > Cover and the page's cover on for the viewer (Studio > Pages > Home > Cover). Buttons over it are glass, as UNA styles every button in a cover. The home menu block is a grid of tiles because the menu's App config says `"view": "grid"` (`getMenuView`); `components/elements/menu-grid.tsx` draws it as UNA's site does (32px icons without a circle, tiles 8px from the block's edges with 12px corners, the sliding highlight), unlike the launcher's circles, with the main menu's animated icons.
